# V1.1 Current Web Bot Auth Alignment Design

Status: living design aligned against direct primary-source reviews through 2026-08-15.

## Goal

Strengthen ATI's experimental Web Bot Auth implementation against the current protocol family without changing V0/V1 privacy, scoring, observe-only, or offline-default guarantees.

The core rule is that **current protocol semantics, deployed compatibility, and historical draft behavior are separate profiles**. ATI must never silently promote a historical compatibility path into the current IETF path, and it must never infer trust from syntax alone.

## Source authority and current implementation profile

ATI currently pins the following implementation profile:

- RFC 9421 — HTTP Message Signatures.
- `draft-meunier-webbotauth-httpsig-protocol-01` in `StandardsProfile`.
- `draft-meunier-webbotauth-httpsig-directory-00`.
- `draft-meunier-webbotauth-registry-03`.
- `draft-illyes-webbotauth-jafar-00`.

The upstream source repository linked by the IETF drafts now contains `draft-meunier-webbotauth-httpsig-protocol.md` as the working protocol source. General Datatracker/search indexes can lag document replacement metadata, so ATI source-health must resolve the direct Datatracker document/version metadata and the upstream draft source before changing a pinned revision.

`draft-meunier-web-bot-auth-architecture-05` and `draft-meunier-http-message-signatures-directory-05` are historical inputs to this branch, not current ATI provenance labels. Existing deployed implementations may still intentionally target older revisions; those are explicit interoperability profiles.

## Trust model

Web Bot Auth authentication proves a cryptographic relationship; it does not prove benign behavior, authorization, or intent.

ATI keeps the existing V1 binding scopes:

- `KEY`: possession of a verification key is proven, but no provider/agent binding is established.
- `PROVIDER`: evidence binds a provider/operator but not necessarily the exact agent token.
- `AGENT`: authority-bound evidence identifies the exact configured agent.

Authentication changes `identity_confidence`. It does not directly reduce `risk_score`, `automation_score`, or `ai_score`.

For current HTTP-signature discovery, ATI treats the resolved **(identifier URL, verification key)** association as the important identity pair. A request-controlled unresolved URL remains a claim, not identity.

## 1. Generic CIMD JWK Set vs HTTP Message Signatures Directory

Registry-03 Agent Cards use normal JWK Set semantics for `jwks`. Directory responses use the stricter HTTP Message Signatures Directory semantics.

ATI therefore keeps two independent parsers:

### Generic JWK Set

- public JWK material is validated;
- private JWK material is rejected;
- RFC 7638 thumbprint is computed independently;
- operator-provided `kid` may differ from the thumbprint;
- parsing alone never promotes the key to trusted agent identity.

### HTTP Message Signatures Directory

- public JWK material is validated;
- private JWK material is rejected;
- a key identity is its RFC 7638 thumbprint;
- Directory-profile `kid` must match the thumbprint when present;
- provenance is `draft-meunier-webbotauth-httpsig-directory-00`;
- HTTP(S) responses must use `application/http-message-signatures-directory+json`.

This separation is already implemented and must not be collapsed.

## 2. CIMD `client_id` retrieval

Registry-03 keeps the CIMD identity model. V1's existing card shape is therefore retained:

- top-level `client_id`, `client_name`, `client_uri`, `logo_uri`, `contacts`, `jwks_uri`, `jwks`;
- bot-specific metadata under `web_bot_auth`;
- `jwks_uri` and `jwks` are mutually exclusive;
- unknown `web_bot_auth` members are ignored;
- `ips_uri` remains a separately typed source.

Client-ID retrieval is intentionally stricter than ATI's generic source fetcher:

- GET only;
- exact HTTP 200 only;
- no redirects;
- returned `client_id` must equal the requested URL by simple string comparison;
- normal ATI SSRF/public-address/TLS protections still apply.

Request-controlled unknown client IDs remain unfetched under the default `registry_only` policy.

## 3. `Signature-Agent` discovery profiles

The current IETF path uses one dictionary parser profile with explicit discovery mechanisms:

- `directory` — default when `type` is absent;
- `jwks_uri` — URI resolves to a generic JWK Set;
- `cimd` — URI is a CIMD `client_id` / Signature Agent Card identifier.

Unknown discovery types are ignored. ATI must not infer the mechanism from URI path, media type, or response body.

Malformed current-profile syntax never silently falls back to a historical parser.

### Cloudflare deployed compatibility

Cloudflare currently documents a deployed interoperability profile based on:

- Ed25519 request verification;
- Directory-03-style key-directory behavior;
- structured-string `Signature-Agent`;
- rejection of the later dictionary form in Cloudflare's own verification path.

ATI supports this only as explicit `cloudflare-legacy` interoperability. It does not redefine the current IETF profile.

## 4. Directory response authority binding

Current directory semantics allow a verifier to preserve the association between a key and the authority that published it, including when directory material is redistributed.

ATI now implements response binding with the following invariants:

- validate `Content-Digest` against the exact response body;
- verify RFC 9421 rather than hand-rolling cryptography;
- require `tag=http-message-signatures-directory`;
- require signed `@authority` with `req` context;
- require signed `content-digest`;
- select the response signature by the expected key thumbprint / `keyid`;
- derive one privacy-safe `KeyAuthorityBinding` per successfully bound key;
- persist only the derived authority, thumbprint, body SHA-256, verification time, optional cryptographic expiry, and standards profile;
- never persist raw `Signature`, `Signature-Input`, or raw signature bytes.

A `304 Not Modified` reuses the stored representation and therefore preserves an existing valid `KeyAuthorityBinding`. Revalidation may update HTTP freshness metadata, but it must not silently renew the binding's cryptographic `verified_at` or `expires_at`.

### Compatibility policy

Response binding is **stronger evidence when available**, but V1.1 does not globally require it for every deployed provider profile yet. For example, current Google deployment documentation describes its signed-agent identifier and well-known directory but does not currently document the newer response-binding behavior as a prerequisite.

ATI therefore keeps protocol capability separate from provider compatibility policy. A later explicit strict profile may require authority-bound directory responses without breaking known deployed interoperability.

## 5. Registry and `data:` discovery

Registry-03 registries may reference HTTPS or `data:` Agent Cards. Current directory semantics also define a `data:` directory form for `type=directory` using the directory media type.

V1.1 may support both only as bounded offline parsing:

- no network I/O for `data:`;
- strict media type validation;
- hard decoded-size limit before expensive parsing where possible;
- explicit percent/base64 validation;
- no private key or secret handling;
- parsed metadata remains self-asserted until independently authority-bound.

HTTPS registry/card/directory fetches continue through ATI's source-trust and SSRF protections.

## 6. Source cache and provenance

ATI source storage is content-addressed where practical and keeps:

- canonical configured source URI;
- source type/provider/binding scope;
- retrieval/freshness metadata;
- content SHA-256;
- parser/standards profile;
- validation state;
- derived key-authority bindings where cryptographically established.

Remote signature headers are ephemeral verification inputs, not stored provenance data.

Search indexes are not authoritative for draft revision selection. Source-health must check direct Datatracker document/version metadata and report drift for review rather than silently rewriting parser or trust policy.

## 7. Identity semantics

Existing resolver remains authoritative:

- key proof alone => `KEY` scope;
- provider-bound evidence => `PROVIDER` scope;
- exact authority-bound signed agent mapping => `AGENT` scope;
- strong incompatible bindings => `CONFLICTED`;
- `UNAVAILABLE`, `STALE`, unsupported syntax, and operational `ERROR` do not become `FAILED` by themselves.

Self-declared `purpose`, robots compliance, rate expectations, or targeted content never lower risk or raise identity confidence merely because a card parses.

## 8. Privacy and security invariants

No raw source IP, signature bytes, Authorization values, cookie values, private key material, or unbounded fetched metadata may enter `Detection` serialization, long-term logs, or source-cache metadata.

Unknown request-controlled discovery URLs are never fetched by default.

Core remains zero-runtime-dependency. Cryptographic verification remains in the optional `[verification]` extra.

PR CI remains hermetic and performs no live DNS/HTTP.

## 9. `Signature-Key`

Registry/protocol work may reference `Signature-Key` as a composable mechanism, but ATI V1.1 does not invent a `client_id` or trust scheme for it. Unsupported syntax remains unsupported until a concrete interoperable contract is defined and reviewed.

## Tests

CI remains hermetic. The regression set covers or must cover:

- generic inline `jwks` accepting operator-defined `kid` while computing a separate thumbprint;
- strict directory parser rejecting mismatched Directory `kid`;
- private JWK rejection;
- client-ID no-redirect / 200-only / exact-match policy;
- unknown client ID not fetched under registry-only default;
- `Signature-Agent` dictionary discovery for `directory`, `jwks_uri`, and `cimd`;
- unknown type ignored and no current-profile -> legacy silent downgrade;
- explicit Cloudflare legacy structured-string compatibility;
- response binding by keyid/thumbprint;
- wrong/missing request authority binding rejected;
- body digest tampering rejected;
- multiple response signatures selected by expected keyid;
- derived bindings serialized without raw signatures;
- `304` preserves existing binding without renewing cryptographic timestamps;
- directory media type enforcement;
- bounded offline `data:` parsing;
- V0 output unchanged and only identity confidence directly affected by identity verification.

## CI and source health

- Core + verification matrices remain required on Python 3.11/3.12/3.13.
- Coverage floor remains >=85%.
- Package wheel/sdist clean-install smoke remains required.
- CodeQL and Dependency Review remain required.
- Deterministic PR CI performs no live DNS/HTTP.
- Scheduled/manual source-health reports standards/provider drift but never silently mutates trust policy.

## Non-goals

- enforcement/blocking;
- anonymous bot authentication;
- speculative `Signature-Key` identity semantics;
- registry push callbacks;
- exact LLM/model inference;
- ML calibration/drift models in this slice;
- browser JS fingerprinting;
- automatic trust of Agent Card intent/compliance claims.

## Acceptance criteria

1. Registry-03/CIMD identity semantics remain intact.
2. Generic `jwks` is not conflated with HTTP Message Signatures Directory key identity.
3. Client-ID retrieval obeys GET/200/no-redirect/exact-match semantics.
4. Current dictionary discovery supports `directory`, `jwks_uri`, and `cimd` without arbitrary request-controlled fetching.
5. Cloudflare legacy syntax is explicit and isolated.
6. Directory response binding is representable as privacy-safe derived evidence.
7. `304` does not erase or renew an existing cryptographic binding.
8. Directory HTTP responses require the current directory media type.
9. Current standards provenance never reports a replaced directory draft as current.
10. Bounded `data:` support, when enabled, is offline-only.
11. No implicit network behavior is introduced.
12. V0 output, scoring separation, and privacy invariants remain intact.
13. Core stays zero-runtime-dependency; verification stays optional.
14. Same-head CI, CodeQL, Dependency Review, package build, and final review were green before PR #8 merged.
