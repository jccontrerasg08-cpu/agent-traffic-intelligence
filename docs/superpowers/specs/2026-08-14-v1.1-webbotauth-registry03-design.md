# V1.1 Current Web Bot Auth Alignment Design

Status: approved direction; corrected against live IETF Datatracker on 2026-08-14.

## Goal

Strengthen ATI's experimental Web Bot Auth implementation against the currently published protocol set without changing V0/V1 privacy, scoring, observe-only, or offline-default guarantees.

## Current primary-source profile

ATI V1.1 targets:

- RFC 9421 — HTTP Message Signatures.
- `draft-meunier-web-bot-auth-architecture-05`.
- `draft-meunier-http-message-signatures-directory-05`.
- `draft-meunier-webbotauth-registry-03` (published 2026-06-26).
- `draft-illyes-webbotauth-jafar-00`.

Search indexes are not authoritative for draft revision selection. Source-health must resolve the Datatracker document/version page directly and compare the active revision before proposing any standards change.

## What V1 already gets right

Registry-03 moved Signature Agent Cards to the OAuth/CIMD metadata model. V1's existing parser therefore remains the correct baseline:

- top-level `client_id`, `client_name`, `client_uri`, `logo_uri`, `contacts`, `jwks_uri`, `jwks`;
- bot-specific metadata inside top-level `web_bot_auth`;
- `client_id` is an HTTPS resolvable identity;
- a card fetched through `client_id` must include the same `client_id` value;
- `jwks_uri` and `jwks` are mutually exclusive;
- unknown `web_bot_auth` members are ignored;
- `ips_uri` is HTTPS and points at JAFAR data.

V1.1 must not flatten the card back to registry-02.

## Real gaps to close

### 1. Generic CIMD JWKS vs Directory-05 keys

Registry-03 `jwks` is a normal JWK Set. V1 currently parses inline `jwks` through the strict Directory-05 parser, which requires Directory-specific thumbprint semantics. Separate them.

Create generic `RegistryKey` / `RegistryKeySet` parsing where:

- JWK public material is validated;
- private JWK material is rejected;
- RFC 7638 thumbprint is computed independently;
- an operator-provided `kid` may differ from the thumbprint;
- parsing alone never promotes the key to trusted agent identity.

Directory-05 retains its strict `keyid == RFC 7638 thumbprint` request-verification semantics.

### 2. CIMD client_id retrieval policy

Registry-03 requires client-id retrieval to:

- use GET;
- accept only 200 OK;
- not follow redirects;
- require the returned `client_id` to equal the requested URL by simple string comparison.

ATI's generic hardened fetcher may follow bounded redirects for other source types, so client-id card retrieval needs a stricter policy/adapter rather than weakening the generic source subsystem.

Request-controlled unknown client IDs remain unfetched under default `registry_only` policy.

### 3. Signature-Agent type=cimd

Registry-03 allows a Signature Agent Card to be discovered from a signed `Signature-Agent` dictionary member with `type=cimd`. ATI must represent discovery syntax/profile explicitly:

- `ietf-directory-05` for current dictionary semantics;
- `ietf-cimd-registry-03` for a signed member that resolves a `client_id` card;
- `cloudflare-legacy` for Cloudflare's currently deployed structured-string Directory-03 compatibility.

No malformed current-profile header silently downgrades to legacy syntax.

### 4. Delegated key response binding

When `jwks_uri` delegates key discovery, ATI should validate key-set response signatures when available. For strict policy, only keys with a valid authority-binding response signature are usable for identity verification.

Expected properties:

- RFC 9421 verification;
- one valid binding per accepted key;
- `tag=http-message-signatures-directory`;
- covered `@authority` with `req` context;
- `keyid` resolves to the corresponding JWK thumbprint for Directory-profile responses;
- `created` / `expires` validated when present;
- invalid/missing binding under permissive policy yields weaker evidence, not maliciousness.

### 5. Registry/data discovery

Registry-03 registry entries are HTTPS or `data:`. V1.1 may support `data:application/json,...` cards only as bounded offline parsing:

- no network I/O;
- strict media type and size limits;
- no embedded secret handling;
- resulting metadata is self-asserted until independently authority-bound.

HTTPS registry/card fetches continue through ATI source trust policy. HTTP is not enabled for registry-03 discovery.

### 6. Registry integrity and cache behavior

Reuse the existing ETag, Last-Modified, Cache-Control and content-addressed source cache. Do not add registry push callbacks in V1.1. If registry response signatures are present, they may be verified in a later slice using the same RFC 9421 primitives, but callbacks remain a non-goal.

## Identity semantics

Existing resolver remains authoritative:

- key proof alone => KEY scope;
- provider-bound evidence => PROVIDER scope;
- exact authority-bound signed agent mapping => AGENT scope;
- strong incompatible bindings => CONFLICTED;
- unavailable, stale, unsupported or operational errors do not become FAILED by themselves.

Self-declared `purpose`, robots compliance, rate expectations or targeted content never lower risk or raise identity confidence merely because a card parses.

## Privacy

No raw source IP, signature bytes, Authorization, cookie values, private key material or unbounded fetched metadata may enter `Detection` serialization, logs or exception text.

Registry/card fetch access patterns are sensitive operational data; source-health and debug output should retain only privacy-safe provenance/digests.

## Cloudflare compatibility

Cloudflare currently documents a deployed Web Bot Auth profile using:

- Ed25519 verification;
- Directory-03-style key directory;
- structured-string `Signature-Agent`;
- rejection of later dictionary form for Cloudflare's own verification path.

ATI supports this only as an explicit interoperability profile. It does not redefine the current IETF profile.

## Signature-Key

Registry-03 mentions `Signature-Key` only as a future composable carrier and explicitly does not define a `client_id` scheme. V1.1 must not invent one. Parse/ignore as unsupported only if encountered; no trust promotion.

## Tests

CI remains hermetic. Add tests for:

- generic inline `jwks` accepting an operator-defined `kid` while computing a separate thumbprint;
- strict Directory-05 parser continuing to reject mismatched Directory `kid`;
- private JWK rejection in both models;
- client_id fetch no-redirect / 200-only / exact-match policy;
- unknown client ID not fetched under registry-only default;
- signed `Signature-Agent` dictionary member with `type=cimd`;
- unsigned or substituted CIMD member rejection;
- explicit Cloudflare legacy structured-string compatibility;
- no current-profile -> legacy silent downgrade;
- valid and invalid per-key delegated-directory response bindings;
- strict vs permissive binding policy;
- bounded offline `data:application/json` card parsing;
- no raw sensitive values in serialized evidence/errors;
- V0 output unchanged and only identity confidence directly affected by identity verification.

## CI/source health

- Existing core + verification matrices remain required on Python 3.11/3.12/3.13.
- Deterministic PR CI performs no live DNS/HTTP.
- Scheduled/manual source-health resolves exact Datatracker document metadata and reports revision drift.
- Drift creates review output only; it never silently rewrites parser/trust policy.
- CodeQL and Dependency Review remain required.

## Non-goals

- enforcement/blocking;
- anonymous bot authentication;
- implementing a speculative Signature-Key client-id scheme;
- registry push callbacks;
- exact LLM/model inference;
- ML calibration/drift models;
- JA4H or license-incompatible fingerprint code;
- automatic trust of card intent/compliance claims.

## Acceptance criteria

1. Registry-03 remains the pinned current Agent Card profile.
2. V1's CIMD shape and client_id identity semantics remain intact.
3. Inline generic `jwks` is not conflated with Directory-05 strict key identity.
4. Client-id card retrieval obeys GET/200/no-redirect/exact-match semantics.
5. Signed `type=cimd` discovery is supported without arbitrary request-controlled fetching by default.
6. Cloudflare legacy syntax is explicit and isolated.
7. Delegated key response binding can be represented and enforced by policy.
8. Bounded `data:` cards are offline-only.
9. No implicit network behavior is introduced.
10. V0 output, scoring separation and privacy invariants remain intact.
11. Core stays zero-runtime-dependency; verification stays optional.
12. All CI/security gates stay green.
