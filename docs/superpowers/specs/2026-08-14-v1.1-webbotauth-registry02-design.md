# V1.1 Web Bot Auth Registry-02 Alignment Design

Status: written review required before implementation.

## Goal

Align ATI's experimental Web Bot Auth support with the currently published primary-source specifications while preserving the green V1 baseline and all V0/V1 privacy, scoring, and offline-default guarantees.

## Source-of-truth standards

As reviewed on 2026-08-14, ATI V1.1 targets:

- RFC 9421 — HTTP Message Signatures.
- `draft-meunier-web-bot-auth-architecture-05`.
- `draft-meunier-http-message-signatures-directory-05`.
- `draft-meunier-webbotauth-registry-02`.
- `draft-illyes-webbotauth-jafar-00`.

The repository must not claim conformance to a draft revision that is not published in the IETF Datatracker.

## Confirmed V1 drift to correct

Current V1 pins `draft-meunier-webbotauth-registry-03` and its Agent Card parser follows a shape that does not match registry-02. Registry-02 uses a flat JSON object with optional parameters such as:

- `client_name`
- `client_uri`
- `logo_uri`
- `contacts`
- `expected-user-agent`
- `rfc9309-product-token`
- `rfc9309-compliance`
- `trigger`
- `purpose`
- `targeted-content`
- `rate-control`
- `rate-expectation`
- `known-urls`
- `jwks_uri`
- `ips_uri`
- `keys`

Registry-02 does not define V1's `client_id` requirement, nested `web_bot_auth` object, or `jwks` field. Unknown parameters must be ignored. At least one recognized parameter must be present. If both `jwks_uri` and `keys` are present, `jwks_uri` takes precedence for key discovery.

## Design principles

1. The current green V1 head remains frozen. V1.1 is developed on a new branch after written approval.
2. No identity change directly modifies `automation_score`, `ai_score`, or `risk_score`.
3. Raw IPs, signature bytes, Authorization, cookies, private keys, and other sensitive material never enter persisted detections.
4. `ati analyze` remains offline by default and never performs implicit source refresh.
5. Operational failures (`UNAVAILABLE`, `STALE`, `ERROR`) never become maliciousness or identity failure by themselves.
6. A valid RFC 9421 signature proves only what is actually covered and bound.
7. Provider-, key-, and agent-scope evidence remain distinct.
8. Draft behavior remains versioned and explicitly labeled experimental.

## Agent Card parser

Replace the current registry-03-shaped parser with a registry-02 parser.

### Required behavior

- Parse the flat registry-02 field set.
- Preserve unknown fields only if needed for diagnostics; they must not affect trust or scoring.
- Ignore unknown parameters for conformance.
- Validate field types independently.
- `trigger` accepts only `fetcher` or `crawler` when present.
- `jwks_uri` and `ips_uri` must pass ATI source-trust URI policy before network use.
- `keys` is parsed as a JWKS-like key set only for Agent Card use.
- When `jwks_uri` is present, it is authoritative for key discovery over inline `keys`.
- Self-asserted metadata such as `purpose`, rate expectations, robots compliance, and targeted content is never authority-bound merely because the card parsed successfully.

## Directory vs generic Agent Card keys

Keep HTTP Message Signatures Directory semantics separate from generic Agent Card key material.

### Directory keys

Directory-05 requires request-signature `keyid` values to be RFC 7638/JWK thumbprints and recommends response signatures that bind each published key to the directory authority.

ATI keeps strict directory semantics:

- compute RFC 7638 thumbprint;
- require Web Bot Auth request `keyid` to resolve to that thumbprint;
- validate key activity windows;
- preserve key type/algorithm compatibility checks;
- reject private JWK material.

### Agent Card inline keys

Inline `keys` in registry-02 are metadata/key material supplied by a Signature Agent Card. They are not promoted to trusted identity solely by parsing. Their trust depends on how the card itself was discovered and whether the relevant response/binding signature is verified.

## Directory response binding

Add a separate response-verification layer for directory key binding.

When directory response signatures are present:

- verify RFC 9421 response signatures;
- require the expected directory tag `http-message-signatures-directory`;
- verify the directory authority binding, including the required request-context `@authority;req` semantics from directory-05;
- require `keyid` to equal the corresponding JWK thumbprint;
- validate `created` / `expires` when present;
- ignore directory keys that lack a corresponding valid binding signature when strict response-binding policy is enabled.

Because directory-05 uses SHOULD/RECOMMENDED language for response signing, absence of such signatures is not automatically `FAILED`. ATI exposes a policy mode so deployments can require strict binding or accept HTTPS-only directory transport as weaker evidence.

## Signature-Agent compatibility

Directory-05 and architecture-05 define `Signature-Agent` as a Structured Field Dictionary whose string members contain URI references. If a member is used for Web Bot Auth identity discovery, one member must be covered by the verified HTTP Message Signature.

ATI keeps two explicit profiles:

- `ietf-dictionary-05`: current draft-compatible dictionary parsing and key-label binding.
- `cloudflare-legacy`: deployed Cloudflare compatibility where `Signature-Agent` is a structured string rather than dictionary.

Legacy compatibility must never silently redefine the standards profile.

## Source URI policy

The drafts allow HTTPS, HTTP, and `data:` URI forms for some discovery paths. ATI V1.1 applies a stricter security policy:

- network fetching: HTTPS only by default;
- HTTP: parsed as an unsupported/insecure discovery URI unless an explicit experimental policy enables it;
- `data:`: may be parsed offline under strict media-type/size validation, never as a network fetch;
- request-controlled unknown URLs are not auto-fetched under default `registry_only` policy;
- redirects are revalidated through the hardened source fetcher.

## Provider profiles

Provider-specific differences remain declarative. No provider-specific branch may bypass the common verification resolver.

Profiles may specify:

- canonical Signature-Agent identity URI;
- directory URI;
- expected interoperability profile;
- allowed legacy syntax;
- binding scope;
- source trust/freshness policy.

Google-style identity URI vs directory URI remains supported as a data-driven distinction.

## Identity resolution

The existing resolver remains authoritative.

- valid key proof without trusted agent binding => KEY evidence only;
- trusted directory binding without exact agent binding => PROVIDER/KEY depending on profile;
- valid signed Signature-Agent plus trusted exact agent mapping => AGENT evidence;
- strong incompatible bindings => `CONFLICTED`;
- timeouts, stale sources, unsupported profiles, malformed optional metadata, or unavailable crypto => never `FAILED` by themselves.

## Testing

CI remains hermetic. Required new tests:

- registry-02 canonical flat Agent Card fixture;
- unknown field ignored;
- no recognized field rejected;
- `jwks_uri` precedence over `keys`;
- malformed URI/type cases;
- self-asserted metadata cannot raise identity confidence by itself;
- directory response signature valid per key;
- missing/invalid per-key directory binding under strict vs permissive policy;
- wrong response tag;
- wrong `@authority;req` binding;
- wrong JWK thumbprint/keyid;
- Cloudflare legacy structured-string compatibility;
- current dictionary Signature-Agent with matching signed member;
- unsigned/substituted Signature-Agent rejection;
- offline `data:` parsing limits;
- default rejection of HTTP network discovery;
- no raw sensitive data in detection serialization or exception text.

## CI and source health

- Existing core and verification matrices remain required.
- Add standards-drift checks that compare pinned revisions against IETF Datatracker metadata in scheduled/manual source-health only, not deterministic PR CI.
- A newly published draft must open a review event; it must not silently rewrite parser behavior or trust policy.

## Non-goals

V1.1 does not add:

- enforcement/blocking;
- anonymous bot authentication;
- JA4H or other license-incompatible fingerprint implementations;
- ML calibration;
- exact LLM/model inference;
- registry push callbacks;
- certificate-chain delegation (`x5c`, AIA, `x5u`) beyond parsing/explicitly unsupported evidence;
- automatic trust of Agent Card purpose/compliance claims.

## Acceptance criteria

1. `StandardsProfile` pins only currently published revisions.
2. Registry-02 Agent Cards parse according to the flat published schema.
3. The current registry-03-shaped parser contract is removed or isolated as unsupported legacy data, never presented as current IETF conformance.
4. `jwks_uri` takes precedence over `keys`.
5. Directory-05 keyid/thumbprint semantics remain strict.
6. Directory response binding can be verified per key and represented as evidence.
7. IETF dictionary and Cloudflare legacy `Signature-Agent` profiles are distinct.
8. No new implicit network behavior is introduced.
9. V0 output remains unchanged when verification is disabled.
10. V1 scoring separation and privacy invariants remain intact.
11. Existing CI/CodeQL/Dependency Review gates stay green.
12. New tests cover all conformance and downgrade/fallback boundaries above.
